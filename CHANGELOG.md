# Changelog

Material changes to `@ethosagent/cli` and its workspace packages. Release-versioned history lives in `docs/content/changelog.md`; this file tracks unreleased schema-governance changes that require a justification per CONTRIBUTING.md.

## Unreleased

### Security

- **`fs_reach` was lexical only — a symlink planted inside an allowed prefix resolved outside it (security-boundary G11).** The personality filesystem boundary judged paths with `normalize(resolve())`, which is a string operation, while a symlink is a filesystem fact. A link at `<allowed>/notes.md → ~/.ssh/id_rsa`, or a symlinked *parent* such as `<allowed>/data → /etc` behind an ordinary leaf, satisfied the `fs_reach` allowlist **and** the always-deny floor, because the floor's guarantee was only "this path string is not a sensitive path" — never "this read does not reach a sensitive file."

  **Fixed at both filesystem boundaries.** `ScopedFsImpl.checkReach` (`packages/core/src/scoped/scoped-fs.ts`) and `ScopedStorage.check` (`packages/storage-fs/src/scoped-storage.ts`) now walk every path segment below the matched prefix with `lstat`, and on finding a link **resolve and re-judge** — the allowlist and the deny floor are both re-applied to the link's actual target — rather than refusing any symlink outright, so ordinary operator layouts (`/var` → `/private/var` on macOS) keep working. Each hop re-walks from the prefix that now contains the path, bounded at 32 hops. The lexical layers are still judged first and with no filesystem access at all, so a path outside the reach is refused on its string form and never reaches an `lstat` — the boundary leaks no existence information about paths it does not govern. The two implementations are deliberately duplicated (core may not runtime-import `@ethosagent/storage-fs` under the new security-kernel layer) and each now carries a reciprocal "these must change together" pointer at the other.

  **This closes misdirection, not TOCTOU.** An attacker who can swap a path between the walk and the subsequent `open` still wins. Closing that half needs kernel-tied operations (`openat` + `O_NOFOLLOW`) or container-level remediation, and remains open.

  **The documentation was wrong for a release.** `docs/content/security/controls.md` published this defense as *Shipped* while the code did not implement it: the original per-tool `realpath()` calls were removed during a refactor that centralised normalisation at the boundary — correct for lexical traversal, silently dropping the symbolic case — and no test, validator, or reviewer prompt failed. Four security pages were corrected (`controls.md`, `overview.md`, `threat-model.md`, `security-fixes.md`), and the new architecture validator now ties every published claim to a `file:line` enforcement point in both directions so a control cannot outlive its code again.

### Changed

- **WIDENING — `packages/plugin-sdk` moved from Tier 2 to Tier 1 (security-boundary Phase 5).** The package was published in `.architecture-state.yaml` and `docs/content/security/security-boundary.md` as Tier 2 — *not owned*, out of disclosure scope, a bug triaged on the normal queue. That is no longer what we say about it. It is now Tier 1, and the promise attached to Tier 1 is a commitment we are taking on, not a label: a report against this package is **in disclosure scope**, it gets a **fix-or-ETA acknowledgement under 90-day coordinated disclosure**, a change to it needs **two maintainers** rather than normal review, and it is held to Tier 1's test bar — **adversarial tests for the boundary it sits on**, which this package does not have yet and now owes.

  **Why.** The 2026-08-12 plugin-loader audit, finding PL-003, and it is a one-line argument: `packages/plugin-sdk` is a credential store. `credPath()` (`packages/plugin-sdk/src/index.ts:628`) resolves `<basePath>/credentials/<key>`, and `hasSecret`/`getSecret`/`setSecret` (`:632-655`) read and write plugin credential material at that path. `setSecret` writes the value through `Storage.writeAtomic` with no `mode`, and never through `SecretsResolver` — which G-SEC publishes as the **sole** storage and retrieval path for credential material. A package that writes secrets to disk sits on a trust boundary regardless of which directory it lives in, and Tier 2 said we were not looking.

  **This widens the roster; it does not repair the guarantee.** PL-003 remains open. G-SEC still claims a sole storage path that this package is a second instance of, and moving the package into disclosure scope changes who owes a response, not whether the claim is true. The repair — route plugin credentials through `SecretsResolver`, or narrow G-SEC's wording to what actually holds — is tracked as a Phase 5 follow-up and is not in this change. Recorded here because a widening is still a change to a published promise, and the direction it moves in is not a reason to skip the note.

  **Corrected count.** The tier header in `.architecture-state.yaml` and the rosters in `docs/content/security/security-boundary.md` and `SECURITY.md` now all read **10 at Tier 0, 23 at Tier 1, 86 at Tier 2** (119 total), mechanically counted from the sidecar after this edit. This supersedes the count in the entry below. The published roster was separately three demotions stale — it still listed `execution-ssh`, `execution-process-backend`, and `sandbox-docker` under Tier 1 — and has been corrected in the same pass; no validator rule catches doc/sidecar tier drift today, which is a gap of its own.

- **NARROWING — `execution-process-backend` and `execution-ssh` left Tier 1 for Tier 2 (security-boundary Phase 5).** Both packages were published in `.architecture-state.yaml` and `docs/content/security/security-boundary.md` as Tier 1 — *in disclosure scope with a stated response commitment*, the "we review this hard" promise. That promise is withdrawn. They are now Tier 2: **not owned**, inheriting exactly what the kernel enforces and nothing more. A report against either package now triages as Tier 2 rather than Tier 1, which is a **weaker** commitment than the one published on 2026-08-12, so it is recorded here rather than quietly amended in the sidecar.

  **Why.** The 2026-08-12 non-docker execution-backends audit found neither package has a reachable production caller. `packages/wiring/src/compose-tools.ts:541` resolves the single literal `'docker'` and no other backend name, and it is the only `executionBackends.resolve(...)` call site in the workspace. `execution-ssh` *is* registered (`packages/wiring/src/build-infrastructure.ts:254`) but never resolved, and `ExecutionBackendConfig.ssh` (`packages/types/src/execution.ts:177`) has no writer anywhere in the repo — so no line of it can execute in production. `execution-process-backend` is a reference plugin: it registers under the namespaced name `<pluginId>/process` (`packages/plugin-sdk/src/index.ts:606`), is depended on by nothing, and ships zero tests. Tier 1 spends review attention and a disclosure commitment on code that cannot run.

  **This narrows the roster, not the guarantees.** No row in the guarantee register cites either package, so no `G-*` guarantee weakened. The reversal is pre-committed rather than left to judgement: `execution-ssh` returns to Tier 1 **the day `ExecutionBackendConfig.ssh` acquires a writer**, since that is the moment a remote host becomes reachable from a personality; `execution-process-backend` returns the day any resolution path can select it. Both conditions are recorded on the sidecar entries themselves.

  **Corrected count.** This change took the tier header in `.architecture-state.yaml` to **10 at Tier 0, 22 at Tier 1, 87 at Tier 2** (119 total); the `plugin-sdk` promotion above then moved it again, and that entry carries the current figure. Note that the "10 / 25 / 84" figure published in the *Added* entry below was already off by one when written — the `sandbox-docker` demotion in the same day's docker audit took Tier 1 to 24 without updating the header. The counts above are mechanical.

- **BREAKING — `AgentSafety` gains a required `approvalPosture` field.** `packages/types/src/safety.ts` adds `approvalPosture: { kind: 'gated'; policy: string } | { kind: 'ungated'; reason: string }`. Core owns the approval *enforcement point* (the `before_tool_call` modifying hook) but could not see whether any policy was registered behind it, so an embedder that registered nothing got a fully working loop with no gating and **no signal**. The posture is now declared rather than inferred. It is required, not optional, on purpose: an optional field defaults silently, which is the exact gap it closes.

  **Migration.** Every out-of-tree construction of an `AgentSafety` bundle must add the field. Declare `{ kind: 'gated', policy: '<your-policy-name>' }` if you register a `before_tool_call` modifying handler, and `{ kind: 'ungated', reason: '<why>' }` if you deliberately do not. A `gated` declaration with no registered handler now throws the new `ApprovalPostureError` (exported from `@ethosagent/types`, `code: 'approval-posture'`) at the **first tool dispatch** — a wiring bug surfaced as a typed error per §V S7, instead of a loop that silently runs ungated. `ungated` is legitimate but never invisible: it logs one warning through the `Logger` contract naming your reason. The check is a once-per-loop latched guard (`packages/core/src/agent-loop/approval-posture.ts`), not a per-call cost, and runs at dispatch rather than construction because surfaces register their handlers after the loop is built. In-tree, `packages/wiring/src/build-agent-loop.ts` declares `{ kind: 'gated', policy: 'danger-predicate' }`, so anything composed through `@ethosagent/wiring` needs no change.

- **BREAKING — `HookRegistry` gains a required `hasHandlers(model, name)` method.** `hasHandlers(model: 'void' | 'modifying' | 'claiming', name: HookName): boolean` on the `HookRegistry` contract in `packages/types/src/hooks.ts`. It is introspection, not a fourth execution model: it exists so a consumer can verify that a declared policy has an implementation behind it — the `approvalPosture` check above — without *firing* the hook, which would mean invoking real approval logic with a synthetic payload. In-tree there is exactly one implementer (`DefaultHookRegistry`) and zero breakage. **Migration:** out-of-tree implementers of the `HookRegistry` interface must add the method; consumers that only *use* a registry are unaffected.

- **Constitutional — a `security-kernel` layer in ARCHITECTURE.md §II.** **§VI amendment class: Structural.** The layer model gains `security-kernel` as a **sibling of core, not a layer beneath it**: it depends on contracts, core depends on contracts, and neither depends on the other. This formalises a rule the codebase already followed — core must not runtime-import the safety packages — and states why it is load-bearing: a kernel that core could import directly would make the engine unswappable and the kernel unreplaceable. Core reaches kernel capability only through contract types bound by wiring (`type_only_deps: [security-kernel]` in the §IX machine-readable block; the package.json edge is legal, the runtime import is not). Extensions and wiring may depend on the kernel directly.

- **Constitutional — §V S6 sharpened.** **§VI amendment class: Substantive.** The inbound safety-injection pipeline is now stated as *reachable only through the injected safety seam*; no personality, channel, or tool may disable it, **and no schema field may exist whose effect is to disable it**. A personality safety block may only ever narrow what the framework already permits — a field that widens policy is a violation of the rule, not a configuration of it. §IX records the rule as `enforcement: mechanical`, gated by the personality drift gate rather than by review.

- **Constitutional — new §III Law 11: kernel guarantees are not weakenable from outside.** **§VI amendment class: Substantive.** A module outside the security kernel must not be able to weaken a guarantee the kernel enforces, because a guarantee an extension can weaken is not a guarantee. Law 11 has **no §VIII exception path**: an exception permitting a module outside the kernel to weaken a kernel guarantee is precisely the violation the law names, and the exception validator rejects any entry targeting it. No Tier 0 package is eligible for a §VIII exception at all.

- **Deterministic tool-definition ordering at the provider boundary** (local-llm-excellence Lane 2a, eng review D6) — `AnthropicProvider` and `OpenAICompatProvider` (and every provider sharing the openai-compat transport, e.g. Azure) now serialize tool definitions in ASCII-stable name order by default instead of registration order. Tool definitions ship ahead of the messages, so they are part of the cacheable request prefix; registration order was not stable across restarts (MCP/plugin/delegation tools register after loop construction). The ordering is a **caching device, not a priority signal**. This CHANGES the request bytes for every deployment with 2+ tools whose registration order was not already sorted. Escape hatch: `toolOrder: insertion` in `~/.ethos/config.yaml` restores the legacy bytes — a temporary rollback lever, marked for removal one stable release later (tracked in `plan/uncompleted-tasks.md`, D13).
- **Compression summarizer inherits the resolved window and model profile** (local-llm-excellence Lane 5(ii)) — `buildCompressionSummarizer` now threads the SAME window resolution (config > cached probe > catalog > default, eng review D15) and per-model profile (`toolCallFormat`, `maxOutputTokens`, `structuredOutput`) into the summarizer's provider that the main provider gets. Before this the summarizer inherited the 128k provider default — the §0 mis-sizing — so its own compaction arithmetic lied on local setups. Hosted configs without an auxiliary summarizer see no change; the summarizer prompt and call shape are untouched.
- **Window-scaled tool-result budget is LOCAL-ONLY** (local-llm-excellence Lane 1(c)+(a), post-review FIX 1) — the per-turn `resultBudgetChars` scaling (down from the flat 80k with the served window) and the derived `maxSingleToolResultTokens` gate-reserve term now engage ONLY for a detected local runtime or an explicit `context_engine_options.resultBudgetChars`. Hosted providers with small catalog windows (hosted DeepSeek 64k, groq gemma2-9b 8k, mistral 32k rows) keep the flat 80k default and no gate-reserve term — the hosted-parity law: local-model work never changes hosted behavior without a key.
- **Tool results are persisted exactly as the LLM saw them** (Lane 2b) — the injection-defense delimiters (`===TOOL_RESULT_START:<tool>===`) are now part of the stored `tool_result` row instead of being applied only to the live in-turn view. Previously a tool result changed shape between the live turn (wrapped) and every later rehydration of the session (unwrapped), which broke the byte-stable message prefix across turns and restarts — the Hermes #4555 failure class. New restart-prefix tests (`packages/core/src/__tests__/restart-prefix-stability.test.ts`, `extensions/session-sqlite/src/__tests__/restart-prefix-stability.test.ts`) pin `render(loop_messages) == render(reload(persist(loop_messages)))` byte-identically.

### Removed

- **BREAKING — `PersonalityConfig.safety.injectionDefense.enabled` (security-boundary G3).** The master switch that skipped provenance wrapping, the pattern check, and the post-read tool downgrade is gone from the frozen `PersonalityConfig` schema (`packages/types/src/personality.ts`), from the personality parser (`extensions/personalities/src/index.ts`), and from the system-prompt prelude, which is now prepended on every turn unconditionally. It contradicted §V S6 — a personality could opt out of a pipeline the constitution says cannot be opted out of — and it made the published claim "per-personality knobs only ever narrow policy" false. Removing it makes that claim true; the surviving `injectionDefense.classifier` knobs narrow only.

  **Migration: none required, and deliberately so.** A `config.yaml` that still carries `injectionDefense.enabled` is not an error. The key is ignored and injection defense stays **on** — the safe direction. A personality that relied on `enabled: false` to suppress wrapping (tests, headless tooling) will now see provenance fences and the post-read downgrade; that is the intended behaviour, and there is no replacement switch. This does **not** change `.personality-field-count`: `injectionDefense` is a nested key inside the existing `safety` field, not a top-level field.

### Added

- **`AgentSafety` behavioural conformance suite (security-boundary G2)** — `runAgentSafetyConformance()` and `AgentSafetyConformanceResult`, exported from `@ethosagent/core` (`packages/core/src/safety-conformance.ts`). `safety` is required on `AgentLoopConfig`, so a loop cannot be built without one — but nothing verified the injected bundle *did* anything: `sanitize: (s) => s`, an identity `wrapUntrusted`, and a `scopedStorageFactory` that returns its argument all satisfy the type. That is policy present in the type system and absent at runtime. Every assertion is behavioural — feed the kit input it MUST change, check it changed the specific way `packages/safety/` promises — because a structural check ("is `sanitize` a function") is exactly the check a no-op passes. Same `{ passed, failures }` shape as the existing context-engine and execution conformance suites; it reports rather than throws.

- **The security boundary is published: guarantee register, tier roster, triage table, and a validator that ties them to code.** Four artefacts ship together, and downstream consumers and security reporters can act on all of them:
  - `docs/content/security/security-boundary.md` — the guarantee register (ten named guarantees, each with the `file:line` that enforces it) and the tier partition, plus the published **non-boundary** list.
  - `.architecture-state.yaml` — the per-package tier assignment for every workspace package (119 packages: 10 at Tier 0, 25 at Tier 1, 84 at Tier 2), the §II layer path inventory, and the active §VIII exception list (currently empty). Every assignment carries the date it was made, committed *before* any report arrives, so a tier assigned after the fact is visible in `git log` as rationalisation rather than triage.
  - `SECURITY.md`, rewritten around tiers — scope is now defined by **what we published as a guarantee, not by which directory the bug lives in**, with a four-verdict triage table a reporter can run themselves before writing. The load-bearing verdict: *a Tier 2 finding that reaches a Tier 0 guarantee is a Tier 0 finding*, and the fix lands in the kernel rather than at the reporting site.
  - `scripts/check-architecture.mjs` — the mechanical projection of ARCHITECTURE.md §IX, reading the constitution's own rules block plus the sidecar rather than restating them. It checks tier completeness, layer import direction (including core's runtime imports of the kernel, derived from the sidecar), §VIII exception shape and expiry, stale kernel-path references, and — in **both directions** — that every published guarantee cites a live enforcement point and every kernel enforcement point is published by exactly one register row. That bidirectional tie is the G11 lesson made mechanical. Run it standalone with `pnpm check:architecture`; it also runs against the live repository from `packages/types/src/__tests__/architecture-rules.test.ts`, so a boundary violation fails `pnpm test` and therefore `pnpm check`. Rules that cannot be expressed mechanically are reported as UNENFORCED rather than approximated.

- **`ContextEngine.onTurnComplete?()`** (Hermes parity item 7, stage 2) — an **optional** method on the `ContextEngine` contract in `packages/types/src/context-engine.ts`, plus the framework call site that makes it real. **§VI amendment class: Substantive** — an addition to a contract interface under `packages/types/`, requiring two-maintainer approval and this entry. `ContextEngine` joins the §VII frozen-schema roster in the same commit (prose table + the machine-readable `frozen_schemas:` mirror), gated by a new `context-engine-method-count` drift test that enforces `frozen_method_count: 3` / `frozen_methods: [compact, shouldCompact, onTurnComplete]` against both the source and the ARCHITECTURE.md manifest.

  **Obligation on downstream code: none.** The method is optional, so every engine registered out-of-tree via `EthosPluginApi.registerContextEngine` keeps compiling and running unchanged. `PLUGIN_CONTRACT_MAJOR` stays at **4** — per `packages/plugin-contract/src/version.ts`, only a field rename, a field removal, or a *required*-field addition bumps it; `packages/plugin-contract/src/index.ts` is untouched. Making the method required would break third-party engines that never see the SDK bump, for no behavioural gain, so it stays optional deliberately.

  Wired at turn end (`packages/core/src/agent-loop/turn-complete.ts`, called from `maybeConsolidateAtTurnEnd`) **before** the auto-compaction and memory-flush gates, so an engine hears about every turn even when both are disabled. That is the deliberate contrast with `shouldCompact?()`, which is declared but never called — the template and the plugin-SDK reference now say so instead of claiming the framework calls it.

- **`PersonalityConfig.evolution_approval_mode`** (Phase 3a) — governance dial for Expression self-evolution. Not a skill, tool, or memory concern because it governs how the personality's own identity text (the Expression region of SOUL.md) changes. Distinct from `safety.approvalMode`, which gates tool calls, not identity evolution. Bumps `.personality-field-count` from 25 to 26.
- **`PersonalityConfig.nightly`** (Phase 3 / P5) — gates the nightly governed-learning pass and its Personality Judge for this personality (`nightly.enabled`, `nightly.judge.enabled`, `nightly.judge.minInteractions`, `nightly.expression`). Not a skill, tool, or memory concern because it governs how a personality's own identity evolves overnight — which steps of the self-evolution loop run and on what activation threshold. Every field defaults to today's behavior when absent (pass + judge + expression all run), so existing personalities are unaffected. Bumps `.personality-field-count` from 26 to 27.
- **Personality-directory `tools.yaml` sidecar file** (web-search-provider-selection, Phase 1) — a new per-personality artifact holding, per tool, `{ provider, secret }` — the source of truth for a personality's `Personality → tool → secret` binding (`web_search` is the sole consumer in v1). **§VI amendment class: Substantive** (a new personality-directory extension pattern). It is a sibling artifact loaded by `FilePersonalityRegistry`, exactly like `mcp.yaml` — it is **NOT** a field on the frozen `PersonalityConfig` interface, so it does **not** bump `.personality-field-count` and does not touch the personality field-count drift gate. It carries only a secret NAME, never a value (§V S9), so the directory stays shareable and committable. The global `~/.ethos/config.yaml` `toolSettings` map is a demoted FALLBACK layer, not an override.
