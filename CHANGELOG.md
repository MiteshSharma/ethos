# Changelog

Material changes to `@ethosagent/cli` and its workspace packages. Release-versioned history lives in `docs/content/changelog.md`; this file tracks unreleased schema-governance changes that require a justification per CONTRIBUTING.md.

## Unreleased

### Changed

- **`SttProvider` takes the utterance as BYTES, and `transcribe(audioPath)` is gone** (voice V1a, eng-review D4) — **§VI amendment class: Substantive** (a breaking change to a contract interface under `packages/types/`). `SttProvider.transcribe(audioPath: string)` is replaced by `SttProvider.transcribeBuffer(audio: SttAudio)`, where `SttAudio` is `{ data: Uint8Array; mimeType?: string; sampleRate?: number }`. `caps.contractVersion` for STT providers is now `STT_CONTRACT_VERSION` (**2**); `validateVoiceCaps` rejects an STT provider still declaring `1`, because v1 named a method that no longer exists. TTS is untouched and stays at `1`.

  **Additive-then-remove in one change, by explicit decision — there is no deprecation window and no back-compat shim.** A two-signature limbo would have meant every caller and every provider carrying both shapes indefinitely; the repo is small enough to move all of it at once, and a third-party provider gets a compile error plus a conformance error rather than a silent no-op.

  **Why bytes.** An utterance is seconds of 16 kHz mono — tens of kilobytes. Round-tripping it through a temp file cost a write, a read, a permission decision and a cleanup obligation on the most sensitive artifact the system handles, on every turn, so that providers could immediately load it back into memory. Three of the four in-repo providers (`openai-stt`, `groq-stt`, `local-stt`) are OpenAI-compatible multipart uploads that never wanted a path. The fourth, `command-stt`, shells out to a binary and genuinely needs one — so it now writes its own temp file (mode `0o600`, MIME-derived suffix, unlinked in `finally`) and owns its lifetime. Whoever writes captured voice deletes it.

  **Consequences.** `VoiceSessionConfig.pcmToPath` and the wiring-level `createPcmToPath` / temp-file-cleanup wrapper are **deleted**: the utterance-buffered fallback now encodes frames as a WAV in memory via `encodeWav`, so it needs nothing injected and `VoiceSession` construction is total for any configured provider (it previously threw for a batch-only provider with no `pcmToPath`). `buildVoiceStack` no longer takes `storage` or `dataDir`. `apps/web-api`'s `VoiceService.transcribe` no longer touches the disk at all. `Gateway` gains an optional `storage` for reading cached attachment bytes — `AttachmentCache` can write but not read, and the gateway may not use raw `node:fs` (Law 7), so the bytes are read by composing `resolveLocalPath` with `Storage.readBytes` at the call site. Third-party providers: implement `transcribeBuffer`, declare `STT_CONTRACT_VERSION`, and check with the new `validateSttProvider` / `validateTtsProvider`.

- **Deterministic tool-definition ordering at the provider boundary** (local-llm-excellence Lane 2a, eng review D6) — `AnthropicProvider` and `OpenAICompatProvider` (and every provider sharing the openai-compat transport, e.g. Azure) now serialize tool definitions in ASCII-stable name order by default instead of registration order. Tool definitions ship ahead of the messages, so they are part of the cacheable request prefix; registration order was not stable across restarts (MCP/plugin/delegation tools register after loop construction). The ordering is a **caching device, not a priority signal**. This CHANGES the request bytes for every deployment with 2+ tools whose registration order was not already sorted. Escape hatch: `toolOrder: insertion` in `~/.ethos/config.yaml` restores the legacy bytes — a temporary rollback lever, marked for removal one stable release later (tracked in `plan/uncompleted-tasks.md`, D13).
- **Compression summarizer inherits the resolved window and model profile** (local-llm-excellence Lane 5(ii)) — `buildCompressionSummarizer` now threads the SAME window resolution (config > cached probe > catalog > default, eng review D15) and per-model profile (`toolCallFormat`, `maxOutputTokens`, `structuredOutput`) into the summarizer's provider that the main provider gets. Before this the summarizer inherited the 128k provider default — the §0 mis-sizing — so its own compaction arithmetic lied on local setups. Hosted configs without an auxiliary summarizer see no change; the summarizer prompt and call shape are untouched.
- **Window-scaled tool-result budget is LOCAL-ONLY** (local-llm-excellence Lane 1(c)+(a), post-review FIX 1) — the per-turn `resultBudgetChars` scaling (down from the flat 80k with the served window) and the derived `maxSingleToolResultTokens` gate-reserve term now engage ONLY for a detected local runtime or an explicit `context_engine_options.resultBudgetChars`. Hosted providers with small catalog windows (hosted DeepSeek 64k, groq gemma2-9b 8k, mistral 32k rows) keep the flat 80k default and no gate-reserve term — the hosted-parity law: local-model work never changes hosted behavior without a key.
- **Tool results are persisted exactly as the LLM saw them** (Lane 2b) — the injection-defense delimiters (`===TOOL_RESULT_START:<tool>===`) are now part of the stored `tool_result` row instead of being applied only to the live in-turn view. Previously a tool result changed shape between the live turn (wrapped) and every later rehydration of the session (unwrapped), which broke the byte-stable message prefix across turns and restarts — the Hermes #4555 failure class. New restart-prefix tests (`packages/core/src/__tests__/restart-prefix-stability.test.ts`, `extensions/session-sqlite/src/__tests__/restart-prefix-stability.test.ts`) pin `render(loop_messages) == render(reload(persist(loop_messages)))` byte-identically.

### Added

- **`PersonalityConfig.voice`** (voice V1a, eng-review D2) — how a personality SOUNDS: `voice.tts_voice` (TTS voice id), `voice.languages` (BCP-47 tag → voice id), `voice.tier` (`pipeline` | `realtime`), `voice.model` (fast-lane model for spoken turns). Optional; absent means inherit the global `auxiliary.tts.*` config. Bumps `.personality-field-count` from 27 to 28.

  **Why it isn't a skill, a tool, or a memory section — and why it isn't config.** It is none of those because none of them can answer "what does this personality sound like": a skill teaches a procedure, a tool performs an action, memory stores facts. And it is not deployment config because the deployment already owns the axis config should own — *which provider* synthesizes speech. Which voice comes out is the same class of question as `model`: part of who the personality is, travelling with its directory when it is shared or exported. A single global voice would make every personality on one machine sound identical, which is the observable bug this fixes.

  **This is a sanctioned carve-out of a forbidden category, and it is closed at both ends.** `voice_speech_audio` remains a `forbidden_field_categories` entry in ARCHITECTURE.md §VII; the amendment adds a `granted_field_exceptions` entry naming exactly `voice`. Voice *modes*, VAD tuning, per-channel speech affordances, and TTS engine settings are still rejected — they are deployment or per-channel concerns and live in `~/.ethos/config.yaml`. `personality-field-count.test.ts` gained a second assertion that fails if any *other* top-level field matching `/voice|speech|audio|tts|stt|spoken/` appears, so the exception cannot be cited as precedent by a future PR without that gate turning red.

  **Shape on disk.** Dotted keys (`voice.tts_voice:`, `voice.languages.es:`), matching the existing `fs_reach.*` / `memory.options.*` / `nightly.judge.*` convention. `config.yaml` is flat by design and the parser already reads dotted keys, so this needed **zero parser changes**; making `voice` a nested block would have added a second parse path, a second render path, and a raw-block-preservation dance like `safety`'s, for four scalars and a string map.

  **Wired, not decorative.** `resolveVoicePreferences()` in `@ethosagent/core` is the one function that answers the precedence question (language-specific voice > personality voice > global voice, per knob), and `buildVoiceStack().createSession()` consults it for the voice it hands the TTS provider. `renderCharacterSheet()` renders a `## Voice` block — omitted entirely when the personality declares none, since "inherits everything" is not worth a section.

- **`ContextEngine.onTurnComplete?()`** (Hermes parity item 7, stage 2) — an **optional** method on the `ContextEngine` contract in `packages/types/src/context-engine.ts`, plus the framework call site that makes it real. **§VI amendment class: Substantive** — an addition to a contract interface under `packages/types/`, requiring two-maintainer approval and this entry. `ContextEngine` joins the §VII frozen-schema roster in the same commit (prose table + the machine-readable `frozen_schemas:` mirror), gated by a new `context-engine-method-count` drift test that enforces `frozen_method_count: 3` / `frozen_methods: [compact, shouldCompact, onTurnComplete]` against both the source and the ARCHITECTURE.md manifest.

  **Obligation on downstream code: none.** The method is optional, so every engine registered out-of-tree via `EthosPluginApi.registerContextEngine` keeps compiling and running unchanged. `PLUGIN_CONTRACT_MAJOR` stays at **4** — per `packages/plugin-contract/src/version.ts`, only a field rename, a field removal, or a *required*-field addition bumps it; `packages/plugin-contract/src/index.ts` is untouched. Making the method required would break third-party engines that never see the SDK bump, for no behavioural gain, so it stays optional deliberately.

  Wired at turn end (`packages/core/src/agent-loop/turn-complete.ts`, called from `maybeConsolidateAtTurnEnd`) **before** the auto-compaction and memory-flush gates, so an engine hears about every turn even when both are disabled. That is the deliberate contrast with `shouldCompact?()`, which is declared but never called — the template and the plugin-SDK reference now say so instead of claiming the framework calls it.

- **`PersonalityConfig.evolution_approval_mode`** (Phase 3a) — governance dial for Expression self-evolution. Not a skill, tool, or memory concern because it governs how the personality's own identity text (the Expression region of SOUL.md) changes. Distinct from `safety.approvalMode`, which gates tool calls, not identity evolution. Bumps `.personality-field-count` from 25 to 26.
- **`PersonalityConfig.nightly`** (Phase 3 / P5) — gates the nightly governed-learning pass and its Personality Judge for this personality (`nightly.enabled`, `nightly.judge.enabled`, `nightly.judge.minInteractions`, `nightly.expression`). Not a skill, tool, or memory concern because it governs how a personality's own identity evolves overnight — which steps of the self-evolution loop run and on what activation threshold. Every field defaults to today's behavior when absent (pass + judge + expression all run), so existing personalities are unaffected. Bumps `.personality-field-count` from 26 to 27.
- **Personality-directory `tools.yaml` sidecar file** (web-search-provider-selection, Phase 1) — a new per-personality artifact holding, per tool, `{ provider, secret }` — the source of truth for a personality's `Personality → tool → secret` binding (`web_search` is the sole consumer in v1). **§VI amendment class: Substantive** (a new personality-directory extension pattern). It is a sibling artifact loaded by `FilePersonalityRegistry`, exactly like `mcp.yaml` — it is **NOT** a field on the frozen `PersonalityConfig` interface, so it does **not** bump `.personality-field-count` and does not touch the personality field-count drift gate. It carries only a secret NAME, never a value (§V S9), so the directory stays shareable and committable. The global `~/.ethos/config.yaml` `toolSettings` map is a demoted FALLBACK layer, not an override.
